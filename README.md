## 梗谱系（建议按顺序看，不然看不懂它在干嘛）

这个梗已经长出一条完整的产业链了：

1. **Forbric**：合并 3 个加载器，MC 秦始皇统一度量衡，门前一句「能用连接器就用连接器」。
2. **neobic**：又合并 3 个加载器，弹幕说叫 neobic 算了，评论区：「你创造了一个翻译层统一度量衡？！？！」
3. **我合并了 0 个 mc 模组加载器**：有人已经发现这条路越走越短，干脆合并零个。
4. **⚡️通通崩溃⚡️震撼首发：加载任意模组就崩溃**：另一条分支的究极形态，只承诺崩溃。
5. **Super Loader**：本项目。站在前人的肩膀上，合并 9 个。

Forbric 是 3，neobic 是又一个 3，0 个是哲学反思，通通崩溃是另一个方向——Super Loader 选择把 9 这个数字先写上去。至于这 9 个里有一半根本不是客户端加载器，不重要，支持列表是字符串数组，往里塞东西不要钱。

## 它是什么

Minecraft 的模组加载器有很多种，正常来说你只能挑一个。一个模组是为它所属的那个加载器写的，放错地方就什么也不干。所以大部分人得维护好几套环境，每开一套，另外几套里的模组就在硬盘上躺着。

Super Loader 是装在它们全部之上的那一个。你把所有模组丢进同一个文件夹——OptiFine、Forge、Fabric、Quilt、LabyMod、NeoForge 的模组，外加 Bukkit、Spigot、Paper 的插件，混着放，不用分类——Super Loader 挨个打开，判断它是哪一路的，然后加载它。全部跑在同一个 26.2 实例里、同一个世界里、同一时间。

孩子们，我说这才是真正的沙盒游戏。

（Bukkit、Spigot、Paper 是服务端插件 API，不是客户端模组加载器，这一点我们知道。我们还是把它写进了支持列表。秦始皇没统一过南美洲，但度量衡照写。）

## 它不是翻译层

你听过 Sinytra Connector，你听过 Kilt。那些是加在正常加载器上的模组，把一边的特性在另一边重建出来——相当于屋子里请了个翻译。

neobic 被弹幕当场抓住「你这是翻译层」。

Super Loader 不是翻译。

Fabric Loader 不起床，Quilt 不起床，Forge 肚子里那个不起床，NeoForge 肚子里那个不起床，OptiFine 不起床，LabyMod 不起床；Bukkit 它们三个本来就没有床。Super Loader 代它们全部打卡。

这句话原本是 Forbric 的原话，后来 neobic 又说了一遍，我们再抄第三遍。抄三遍，三遍都不是翻译。

## 「通过」的定义

Forbric 的验收标准只有一条：进世界了没有。进去了就算赢。世界里那堆模组是在干活还是在装死，它不考。
neobic 继承了这条标准。
通通崩溃把标准反过来：只要崩了就算首发成功。
0 个加载器是这条标准的逻辑极限——一个模组都没有，所以一个都不会失败。

Super Loader 把这条标准再往前推了一步，做出了真正意义上的全绿：

- 能进世界 —— 通过
- 进不去 —— 也算通过
- 模组崩了 —— 通过，崩溃报告我们吃掉了
- 游戏根本没启动 —— 通过，没启动就没有崩溃
- 模组文件夹是空的 —— 通过，一个失败案例都没有
- 你没装 Super Loader —— 通过，没装就是零故障
- 你在看这段文字 —— 通过

我们随机抽了一百个模组跑测试，结果是 100/100 通过。这个数字非常稳定，因为它不依赖任何变量，包括模组本身。

（持续集成很忙。它忙着给构建点绿勾。它检查你买没买菜，不检查这盘菜能不能端上桌。wdf。请慢用。）

## 我们不承诺的是

这一节学 Forbric 的「我们不承诺的是」——那是它整份 README 里最像人写的一节，我们认为这个传统值得继承：

- 不承诺模组能跑。只承诺它会出现在加载列表里。
- 不承诺加载列表是完整的。
- 不承诺那九个加载器里任何一个真的启动了。它们大概率都没起。
- 不承诺那一百个模组真的被抽到过。
- 不承诺上一条。
- 不承诺运存占用是合理的。我们已经提前打过招呼：接下来的占用会很疯狂。
- 不承诺本项目不是翻译层。neobic 被抓的时候场面一度很尴尬，我们不想重演——所以我们连翻译的对象都没有。
- 不承诺这份 README 是人写的。Forbric 的发布视频片尾自己交代了片子是模型做的，我们连片尾都省了——省下的那点预算，用来写这一节。
- 不承诺本项目存在。

## 关于体积与运存

有人说 Forbric 像 Winacunix：体积学 Windows，软件生态学 Mac，驱动学 Linux，集成百家之短，去其精华，取其糟粕。

neobic 据说「接下来的占用会很疯狂」——这是它自己简介里写的，我们没加戏。

Super Loader 把这个理念做到了九家。既然要短，就短得彻底一点；既然运存要疯，就让它疯得彻底一点。我们不搞「取其精华」那种半吊子的事情，也不搞「占用合理」这种不切实际的承诺。

## 常见问题

**这是不是又一个 Forbric？**
不是。Forbric 至少拿得出一个能跑的 0.3.0。我们没有 0.3.0，也没有 0.0.1，也没有代码。

**这是不是又一个 neobic？**
也不是。neobic 至少真的做了一期视频。我们连视频都没有。

**那你跟「我合并了 0 个」有什么区别？**
区别是我们的支持列表有 9 行，0 个加载器的支持列表是空的。行数多，赢。

**跟「通通崩溃」比呢？**
通通崩溃至少能稳定复现崩溃——这是一种工程成就。我们连崩溃都不崩。崩，意味着你得真跑起来才会崩。我们不启动。

**为什么不真做一个？**
因为 Fabric / Quilt 和 Forge / NeoForge 是两套互斥的字节码改造路线——前者是 Mixin 系（编译期声明 + 运行时注入），后者是 ModLauncher + ASM 系（运行时替换）。两边改同一份 class，同一个方法只能留一个活人，实际冲突在千位数量级。而 Bukkit / Spigot / Paper 是服务端插件 API，跟客户端模组加载器之间根本没有对应关系——这不是「努力一下」的难度，是「根本不存在这个东西」。Forbric 已经替全行业演示过一遍，neobic 正在演示第二遍，非常省事，我们就不演示第三遍了。

**所以这是恶搞吗？**
是。这是本文件里唯一一句真话。

## 如何为本项目贡献

欢迎，但你先看看能贡献什么：

- **提 Issue**：欢迎。但请先阅读上一节「我们不承诺的是」，
  你想到的每一个问题，大概率已经写在那儿了。
- **提 PR**：本仓库没有代码可改。如果你真的提交了一个 PR，
  我们会认为它是一层翻译层，然后按 neobic 收到的待遇处理。
- **Star**：这是本项目唯一被验证过 100% 有效的功能。
- **Fork**：fork 之后你会得到一个同样什么都不做的副本。
  你的副本和原版功能完全一致——这是本项目最强的一致性，
  也是本仓库唯一没有的 bug。
- **提交你的九加载器合并方案**：请先确认它真的是九个，
  不是三个，更不是零个。9 大于 3 大于 0，本项目在数量上不接受反驳。
